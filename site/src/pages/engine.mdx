# Engine

<p class="lede">An engine is the implementation behind a mix. One ships, called <code>mixer</code>, and every mix uses it unless told otherwise.</p>

An engine is three things. A [`name`](Engine.name), for error messages. [`runs`](Engine.runs), the set of patch forms it can run: `'fn'` for patches written as a function, `'keys'` for patches written as keyframes, `'motion'` for a `spring` or `glide`. And `create(kit, opts)`, which builds a mix. Everything on a mix is the engine's to implement.

`mixer` runs all three forms in JavaScript, working out each subject's pose when it is probed. Where every voice writing a channel allows it, it works that channel out for every subject at once at the frame's first probe instead, with the same result; `MixOptions.lanes: false` turns that off, and `mix` from `@msb235/blits/lean` is the same engine with that code left out of the bundle, about a quarter smaller.

To copy those values into each pose quickly, `mixer` writes a small function with `Function` for each set of channels on lanes. A page whose Content Security Policy leaves out `'unsafe-eval'` refuses it, and the browser counts that as one violation: a `securitypolicyviolation` event, an entry in the DevTools Issues panel, and a report to the policy's `report-uri` if it has one. The mix then copies with a plain loop, to the same values, and doesn't ask again while the page is open, so a page sees at most one. A page that must see none uses `lanes: false` or `@msb235/blits/lean`.

You pass a different engine through `MixOptions`:

```ts
const m = mix<Part, PartPose>(PART, { engine: myEngine });
```

A mix refuses a voice its engine can't run. The refusal comes at `cue`, not partway through a frame, and names the engine and the form.

## The GPU engine

`gpu` from `@msb235/blits/gpu` folds voices on the GPU, through WebGPU, for scenes with thousands of subjects all doing the same math: a grid where every pixel is a subject, or a field of instances. Each frame it works out every subject's pose in one compute pass and leaves the result in a GPU buffer, which the host's own shader reads to draw. The site's per-pixel examples run on it.

It folds blits' own patches as they are written for `mixer`: `keys`, `wave`, `tween`, `spring` and `glide`. Register the subjects it folds, in the order their values sit in each buffer, then cue and sync as on any mix:

```ts
import { gpu, gpuOf } from '@msb235/blits/gpu';

const device = await (await navigator.gpu.requestAdapter())!.requestDevice();
const m = mix<Cell, Glow>(K, { engine: gpu({ device }) });
gpuOf(m).subjects(cells, () => ({}));
m.cue({ patch: keys(2000, PULSE, { ease: 'ease-in-out' }), subjects: cells, loop: true });

// Each frame: sync, then bind the channel's buffer in your render pass.
m.sync(now);
const glow = gpuOf(m).channel('glow'); // { buffer, offset, stride, axes }, or null
```

A `spring`, `glide` or `tween` keeps working as on the CPU: a `to()`, `set()` or `push()` lands at the voice's time, though nothing reads the subject on the CPU.

For math no stock patch does, such as a disc whose position each cell is tested against, write a `shaderPatch`, twice: as WGSL for the GPU, and as a JS `at` for everything that runs on the CPU. The WGSL sets `out.<channel>` from `phase`, `pass_index`, `subject.<field>`, and `params.<name>`:

```ts
import { shaderPatch } from '@msb235/blits/gpu';

const band = shaderPatch<Cell, Tint, { y: number }>(0, {
  fields: { y: 'f32' },
  params: { y: 'f32' },
  wgsl: 'let c = select(0.0, 1.0, abs(subject.y - params.y) < 0.1); out.tint = array<f32, 4>(0.7 * c, 0.1 * c, 0.1 * c, c);',
  at: (_phase, cell, _setting, p) => {
    const c = Math.abs(cell.y - p.y) < 0.1 ? 1 : 0;
    return { tint: [0.7 * c, 0.1 * c, 0.1 * c, c] };
  },
  writes: ['tint'],
});

gpuOf(m).subjects(cells, (c) => ({ y: c.y }));
m.cue({ patch: band.with({ y: 0.25 }), subjects: cells });
```

`with` binds a patch's parameters, so one shader serves every band. Both halves give every channel a value for every subject; for a subject a shape misses, that is zero coverage or the rule's rest. A shader can also read per-voice `tables`, a grid of numbers each voice binds through `with`: WGSL reads one as `table_<name>(x, y)` and `at` as `params.<name>(x, y)`, and new contents don't recompile anything. In WGSL, `x` and `y` may be `i32` or `f32`; both sides floor them, and a coordinate outside the table reads 0. In development, the first frame a shader runs reads a sample back and warns where its WGSL and its `at` disagree. `OVER_WGSL` gives a host's shader `toHex`'s arithmetic, laying a color pose over a base.

What runs where:

| On the GPU | On the CPU, as `mixer` runs it |
|---|---|
| `keys` eased by a CSS name, a `bezier` or `steps`; `wave`; `tween`, `spring` and `glide`; `shaderPatch` | `fn` patches. `keys` with an easing function or a `lerpBy` of its own. A motion on an `ink`, which moves round the hue, or eased by a function |
| A voice whose weight is a number (fades included), staggered or not, reaching every registered subject or some of them (`subjects`, `target`) | A weight signal, an owner, a patch with `state`, `from: 'current'`, a bounded voice, or one parting from subjects. A stagger asked as subjects are met (no `subjects` at `cue`) on a voice that ends |
| `sum`, `mul`, `max`, `min`, `norm`, `screen`, `darken`, `vec` of those, `angle`, `color()`, and all 25 color blend modes on `color` or `ink`, roles included | `last`, `quat`, `ink()` and `ink(last())`, `affine` |
| | `probe`, `pull`, `project`, `seek`, history, and the debug panel. A motion voice read back through history or by a projection stays on the CPU that frame |

A voice that can't run on the GPU keeps every channel it writes on the CPU, and the engine warns once in development with the reason, such as `its weight is a weight signal` or `its easing is a function`. `gpuOf(m).channel(name)` returns null for a frame the GPU isn't folding that channel, or while a new kernel compiles; a host then probes on the CPU, as the site's examples do.

The GPU computes in 32-bit floats, and agrees with the CPU to that precision. Where a value jumps — a square wave flipping, a `steps` easing, a keyframe, a loop wrapping — a subject whose time rounds to the other side shows the value from one float step away, a tiny fraction of a millisecond early or late. The GPU's agreement tests allow that one step there and nothing more; a bounded `glide`, whose path depends on which side of an edge it stops, decides that on the CPU in 64 bits.

Measured on teitou (Apple M5 Max) in headless Chromium, a whole frame of three looping `keys` voices, a `wave` and a `spring` retargeting 5% of its subjects each frame, read on `mixer` with `pull` and on the gpu engine until the GPU reports the fold done (medians; `bench/runs/2026-11-03-gpu-stock.txt` and, for the gpu engine with retargets, `2026-11-03-gpu-upload.txt`):

| Subjects | `mixer` | gpu engine | gpu engine, no retargets |
|---:|---:|---:|---:|
| 10,000 | 1.59 ms | 1.04 ms | not run |
| 100,000 | 24.56 ms | 4.19 ms | 0.28 ms |
| 1,000,000 | 300.76 ms | 45.66 ms | 0.39 ms |
| 100,000, staggered | 41.36 ms | 4.48 ms | not run |
| 1,000,000, staggered | 470.57 ms | 53.55 ms | not run |

With nothing retargeted, a million subjects fold in under half a millisecond. With 5% retargeted, at a million subjects the `to()` calls take 14 ms, as they do on `mixer`; preparing the fold, which works out each retargeted subject's new path for the GPU, takes 28 ms, and waiting for the GPU 3 ms.

The staggered rows give every voice a delay of up to about a second, fade the `keys` voices in, and have one of them reach every other subject through `target` (`bench/runs/2026-11-04-gpu-stagger.txt`). Their gpu engine figures come from a later build than the unstaggered rows', so the two don't isolate what staggering costs, and the 1,000,000 median includes the frames where subjects were still fading in.

Measured on the site's examples, on an Apple M5 Max in headless Chromium, the main thread's work per frame, drawing on the CPU and then on the gpu engine (`bench/runs/2026-11-02-demos-*.json`; light board and white balance, as they run on `keys` patches, `bench/runs/2026-11-03-demos-keys-*.json`):

| Example | Subjects | CPU drawing | gpu engine | GPU work, at most |
|---|---:|---:|---:|---:|
| blend modes | 17,136 | 20.83 ms | 1.17 ms | 2.62 ms |
| number rules | 17,136 | 13.97 ms | 2.27 ms | 2.55 ms |
| stack order | 14,400 | 9.69 ms | 1.80 ms | 1.01 ms |
| light board | 10,368 | 8.30 ms | 1.12 ms | 1.90 ms |
| threshold wipe | 12,800 | 4.97 ms | 0.74 ms | 0.84 ms |
| white balance | 10,368 | 4.52 ms | 0.34 ms | 1.23 ms |
| hit flash | 12,800 | 3.20 ms | 0.27 ms | 0.61 ms |

The last column is each frame's submits timed until the GPU reports them done, so it counts waiting as well as work. Number rules keeps its `last` rule on the CPU, which is most of what is left on its main thread. Scenes of tens or hundreds of subjects gain nothing: the site's other examples spend under 0.4 ms a frame in the mix.

## Why the seam exists

A patch written as keyframes is data: its stops stay on the patch as `keys`, and its easing is a CSS name, a `bezier` or `steps` rather than a function. That is so an engine other than `mixer` can read them. Besides the GPU engine above, these are what the seam is judged against, though neither is being built:

- A Web Animations engine that runs `keys` patches only and hands them to the browser, so a page's motion plays off the main thread. It refuses `fn` and `motion` patches at `cue`.
- A recording engine that wraps another and captures every pose as keyframes, turning a procedural patch into data for the first.

An engine can start as a wrapper around `mixer`. This one runs on the CPU like `mixer` does, but declares that it runs keyframes only, so a mix built on it refuses anything else:

```ts
import { type Engine, keys, mix, mixer } from '@msb235/blits';

const keysOnly: Engine = {
  name: 'keys-only',
  runs: new Set(['keys']),
  create: (kit, opts) => mixer.create(kit, opts),
};

const m = mix<Part, PartPose>(PART, { engine: keysOnly });
const rise = keys<Part, PartPose>(400, [
  { at: 0, delta: { gain: 0 } },
  { at: 1, delta: { gain: 1 } },
]);

m.cue({ patch: rise }); // runs
m.cue({ patch: flicker }); // throws: blits: engine keys-only does not run fn patches
```

`mixer` checks each cue against the engine named in the options it was built with, which here is `keysOnly`, so the refusal carries the wrapper's name.
